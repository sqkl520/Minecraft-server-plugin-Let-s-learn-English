## 一句话判决

这是一个由单人在 22 个活跃 git 日内堆到 3.3 万行、自动化测试实覆盖 1.86%、且没有任何一条真实用户证据的功能庞然物——它每修一轮 bug，只是在为"再加一批功能"积累继续的借口，而不是在接近可维护的稳定态喵。

## 论点一：复杂度已超出单人维护极限

**体量事实（本仓实测）**：主代码 88 个 java 文件 / 32,925 行（约 201 个类型声明）；21 张数据表；配置面约 437 个叶子键（config.yml 263 + achievements-config 132 + ai_scenarios 42，顶层 26 段）；i18n 694×2 键；命令面 36 个子命令分支（`/le` 25 个 case + `/lea` 11 个）；19 个 GUI + 15 个 listener；词库 995 词。**维护者 1 人**（git shortlog：77+3 commits 同一作者两邮箱；README 自述"初中生用 AI 做的插件"）。

**比例失衡**：`DatabaseManager.java` 单文件 3,031 行 / 98 个方法 / 79 处 synchronized / 81 处取连接；测试仅 8 文件 754 行，jacoco 门禁被调到 `minimum 0.01`，实测行覆盖 **1.86%**（269 覆盖 / 14,171 未覆盖）、分支 1.35%，`LetsLearnEnglish`、`LearnCommand`、`AdminCommand`、`ConfigManager` 及全部 GUI/listener 均为 **0.0%**。98% 的代码在任何改动下都不穿降落伞。过程文档 138 份 md / 17,843 行（tasks/ 占 10,715 行），**文档行数超过代码行数的一半**——知识不在类型系统里，在注释与 markdown 里，这是"没人敢动"的典型体征喵。

**三个最不可持续的耦合点**：
1. **单连接 + 全局锁 + 内存/DB 双写三元组**。DatabaseManager 把内部监视器交出，库外 8 个文件手写约 40 处 `synchronized(getConnectionLock())`；PlayerDataStore 1,441 行、持 14 个 UUID→Map 缓存，三套一致性语义并存（即时绝对值 UPSERT / miss 回读真源 / 每分钟全量清扫无 dirty flag）。正确性靠"锁内取连接"这类注释约定维持：本轮修了点名的 10 处，`review-complete.md:35/42` 自己承认 DailyChallengeManager 仍有 ~8 处、AchievementManager 仍有 4 处同型问题"**未扩面**"。roadmap 开过的真药方 FIX-STAB-01（SingleThreadExecutor）全库 grep 结果为零——从未落地喵。
2. **GUI 用"标题中英子串 contains"做路由的字符串状态机**。11 个 listener 重复同一判定，`GUIUtils.isPluginGUI`（GUIUtils.java:77-107）再抄一份全量标题清单，注释自认"标题改名不同步=静默丢失音效"；CHANGELOG 记录新 GUI 需"标题避碰实测 16 项断言"。i18n 文案与功能路由焊死：改一条翻译就是一次线上事故面喵。
3. **主类上帝对象 + 服务定位**。`LetsLearnEnglish` 928 行、onEnable 段约 782 行，持 31 个 manager 字段，全库 `plugin.getX()` 式运行期取依赖 1,414 次；构造顺序即生死契约（"OnboardingManager 必须先于 registerListeners"靠注释规定）。加一个新功能横切约 12 个点（新表需手工同步 createTables / schema.sql / deletePlayerData 三处——C-2 批就漏过 `class_members`），而项目内 `interface` 几乎不存在，编译期查不出任何环，所有错配只在运行期爆喵。

## 论点二：产品命题不成立

- **注意力竞争**：MC 是高变率奖励、强视觉运动卷入的多巴胺环境；背单词是高认知负荷的前额叶任务。编码特异性是学习科学常识（context-dependent memory，Godden & Baddeley 1975 潜水实验一系，常识标注）：在游戏语境编码的"词形—词义"联结，提取线索与真实英语使用场景（阅读/听力/写作）几乎不重叠。README 的原话甚至不是"边玩边学"，而是"让你游戏中**强制**学习英语"喵。
- **动机互斥 + 奖励置换**：来 MC 的动机是自主娱乐，强制学习诱发心理阻抗；金币/连击/赛季等外在奖励存在过度辩护效应（Deci 认知评价理论，常识标注），把"学会"置换为"刷完"。这一条不需外部理论，本仓自带实证：H2"开局秒退无限刷 50 金币"、R10-H1"同日重启重复发放挑战奖励"——**系统亲手把玩家的最优策略训练成绕过学习**。签到阶梯、每日提醒、广播鼓励，全是拉 DAU 的手段，不是促学会的手段喵。
- **迁移证据缺失**：系统只记录对错与写死的间隔（1h~168h），没有前后测、没有词汇量基准，没有任何文档回答"用了它的学生英语能力发生了什么变化"。艾宾浩斯参数是常量，它是否优于"不复习"从未被检验——因为从不存在被试喵。

## 论点三：每次修 bug 都在给沉没成本续命

**修复链轨迹**：10-09 路线图核出 19 条（16 CONFIRMED）→ Phase 2 后审查 P0 高危 9 条 + 中危 30 条 → Phase 3 收口 30+ 条 → 10-18 全仓审查 **11 高 / 37 中 / 49 低 = 97 条** → 10-19~20 修复 72 条（9 高 + 35 中 + 28 低）。**每一轮更深的审查都产出更多发现**，这在症状学上正是"把不可靠架构逐点修到看起来可靠"，而非"架构本身可靠"喵。

判据看同族 bug 的繁殖力：锁外取连接在 R3-H3 / R6-L1 / D1 / S2 由不同 agent 反复独立发现，修法一致是"只修点名处"；时区错位族两处发现后才"统一口径"；主线程 IO（export / 午夜 rollover / 日历 GUI / 挑战 GUI / join checkAndAssign）一个接一个移异步——只要单连接 + 全局锁 + 无事务边界不换掉，**"主线程 IO"与"并发双写"这两个类目永远修不完**，因为每个新功能自动获得一批新双写点与新锁窗口。残余台账已给出预告：9 条低优遗留 + 36 条待验证（双服联调、MySQL 整链、备份撕裂概率压测、真实 HTTP 负载）全部需要**实机**，而实机证据恰是本项目最稀缺的喵。

成本核算：18 路施工流 + 11 路红队 + 四份 fix-plan（约 1,400+ 行 md）换来的交付物是"不刷钱、不丢数据、备份可恢复"——这是一只正常插件的**地板**，不是价值。野心曲线同样说明问题：CHANGELOG 单版本篇幅 9 行（v1.0.0）→ 426 行（v1.0.7）；v1.0.7 单版 **Added 110 / Fixed 280 / Changed 9**——修复条目已远超新增，而新增仍以 110 条/版的速度膨胀喵。

## 论点四：缺的是度量不是功能

全库无 bStats、无任何玩家侧遥测。唯一的"仪表盘"是 `StatisticsHttpServer` 自托管 ECharts，统计的是游戏内行为流水（金币、会话数、活跃玩家），**既不统计学习有效性，也不统计功能使用率**喵。

项目史上唯一接近"成功指标"的表述是路线图 Phase 3 出口"新玩家首轮完成率目标 ≥70%（**人工抽测**）"；而 onboarding 计划自己承认精确漏斗口径做不到——`player_data.created_at / last_login` 两列是"DDL 有、全库**零写入点**"的死列（PF-ONB-03，编排者已核实 DatabaseManager.java:115 原注释自陈）。也就是说：**做漏斗分析所必需的最小一列，至今无人写**，同期却上了赛季、班级、HTTP 面板、AI 会话点评喵。

更硬的一条：13 份 findings + 全部 review 文档中，**没有任何一条 bug 或功能决策的来源标注为"真实用户反馈"或"线上数据"**，97 条 findings 全部是程序对程序的静态取证；连"R11 UX 旅程"域都是 agent 走查而非玩家访谈；"运营观察项"仅 1 处（review-complete.md:40）且为自观测。分发面同样无证据：`versions/` 只有 SNAPSHOT JAR、git tag 全是 SNAPSHOT、无 `.github/`（零 CI）、无 GitHub Release。**一个从未证明有人用过的产品，正按每版 110 条新增的速度加功能**——这不是盲飞，这是从未起飞喵。

## 论点五：最理性的路线

我主张 **方案 A 为主干的 D 案（A′：冻结 + 最小可信实验）**喵。

- **拒绝 C（转 B 端 SaaS）**：它需要销售、未成年人数据合规（PIPL/COPPA）、SLA 与运维承诺，与"单人初中生产能 + 零遥测 + 零真实用户"的现状差若干个数量级。把插件降为前端并不会创造需求，只会把一个尚未被证伪也未被证实的命题包装得更贵喵。
- **慎对 B（砍 60% 重写）**：方向对（回到最小学习闭环），但几乎必然把同一套"功能膨胀 + 零度量"的发展模式复刻一遍——重写者最大的敌人是自己的 feature-brainstorming 肌肉记忆。没有度量闸门的 B，只是第二轮 v1.0.7 喵。
- **A′ 具体形态**：功能面全冻结、只做减法——把默认关闭的 season / class-system / statistics-server 整链删除（表面积可再降约 30%），只保留"词库 → 答题 → 艾宾浩斯复习 → 错题本"闭环；补上 `created_at` 的一行 UPSERT 与三个指标：**功能使用率、7 日复习留存、闭环前后词汇自测量表**；找 1~2 个不由作者本人充当玩家/管理员的真实班级环境跑 4 周。信号正向→才值得以产品形态继续；信号缺失或为负→转型为"AI 多智能体编排的工程作品集/教学样本"，README 诚实标注，停止以产品名义迭代喵。

```
决策树
├─ 是否存在 ≥1 个不由作者本人充当玩家/管理员的真实活跃部署？
│   ├─ 否 → 定为"品尝型开源 / 作品集"（A），停止功能迭代，README 诚实化
│   └─ 是 → 立即埋 3 指标：功能使用率 / 复习留存 / 前后测
│         ├─ 4 周后学习有效性无正向信号 → 收敛为最小闭环重写（B 的受控迷你版：先定指标再动手）
│         ├─ 有效但价值仅是"背词小游戏" → 维持 A 冻结态，只修崩溃与数据丢失
│         └─ 有效且有机构主动愿付费     → 才评估 C（插件降为交付前端）
└─ 硬约束：任何新功能提案必须先回答"哪个指标因此上升、怎么测"，答不出即不排期
```

## 反魔鬼自检

若以上论点全错，最可能错在这五处（按可能性排序）喵：

1. **采用率是弱证据推断，我可能严重低估真实用户**。搜索引擎查不到该 repo ≠ 无人使用；插件完全可能通过 QQ 群/校内渠道分发，作者的班级或许正是部署现场。若确有几十名学生日常在用，论点四的"零用户证据"降级为"零用户度量"，论点二也从"命题不成立"退为"命题未被检验"——仍然致命，但语气应从"推倒"降到"先停下来量一量"喵。
2. **我把"人类单人认知负荷"的成本模型套在了 AI 编排项目上**。若作者的有效瓶颈是 token 与额度而非心智带宽，72 条修复的真实人力成本可能远低于我的直觉。自我反驳：1.86% 覆盖率下，AI 修复的正确性同样只靠红队 agent 的阅读理解保证，风险只是换了形态，并未消失喵。
3. **72 条修复不是原地踏步**。刷钱、丢数据、撕裂备份、主线程卡服这些地板级危害确实被抬离地面；插件生态大量优秀作品同样是脏代码，"架构不优雅但能跑"在 Minecraft 插件这一层级是常见且可接受的生存策略——我的"不可持续"判断隐含了偏高的工程标准喵。
4. **游戏化词汇学习并未被判死刑**。教育游戏 meta 分析里存在正向结果（常识标注），MC 的"在场感 + 同伴社交"恰是 Anki 给不了的差异化资产；我的多巴胺论证对"低龄 + 强社交服"场景可能过度悲观喵。
5. **这个项目最大的产出可能是作者本人**。一个初中生借此走完了需求拆解、分层架构、并发一致性、多轮审查、回归核验、i18n、发布纪律的完整链条，且 35 条"已关闭"抽验零虚报（Phase 3 final-review 证实）——**作为工程教育，它已经拿到了全项目唯一可信的"前后测"证据**。"停止迭代"应是对**产品**的判决，不该是对**人**的判决；若这一点被误读，那将是我这份报告里最需要收回的部分喵。
